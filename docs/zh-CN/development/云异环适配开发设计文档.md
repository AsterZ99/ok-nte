# 云异环适配开发设计

本文定义 PC 版云异环的调查边界、接入顺序、风险控制和验收合同。它是施工依据,
不是对云客户端内部实现的既成事实描述。

| 项目 | 值 |
| --- | --- |
| 状态 | Draft, 等待真实云客户端探针数据 |
| 设计基线 | `ok-nte` commit `2f9c479` |
| 框架基线 | `ok-script==2.0.4` |
| 第一目标平台 | Windows 11 |
| 文档更新日期 | 2026-09-15 |

!!! warning "先取证, 后实现"

    云客户端的进程名、窗口类、父子层级、截图目标和输入目标目前均未在本仓库中得到
    实机证据。任何类似 `Qt*QWindowIcon`、`NTECloudGame`、`WLCloudGameClient` 的名称
    都只能作为探针标记词, 不能直接进入正式匹配规则。

## 1. 目标、非目标与安全边界

### 1.1 目标

将云异环作为 `ok-nte` 的第二种 Windows 运行目标, 尽量复用现有任务、OCR、模板、
场景判断和战斗逻辑:

```text
Existing Tasks
      |
ok-script Capture / Interaction
      |
Local NTE or Cloud NTE target
```

第一阶段完成时应满足:

- 本地异环行为不变;
- 云异环能够稳定定位目标窗口并获取纯游戏画面;
- 基础键鼠输入可用, 且失去可信目标后立即停止输入;
- 至少一个已有简单任务不含云端分支即可运行;
- 云端差异不扩散到 `src/tasks/`、`src/combat/` 和 `src/char/`。

### 1.2 第一阶段非目标

- 云平台账号登录、排队、购买时长和复杂重连;
- 自动调整云画质或网络质量诊断;
- 承诺所有输入都能后台执行;
- 声音触发和后台音频路由;
- Windows 10 正式支持;
- 为适配引入进程注入、API Hook、内存读取或大型新框架。

### 1.3 不可破坏的边界

- 仍只通过截图、OCR、系统输出和普通键鼠事件与游戏交互;
- 探针默认只读, 默认不截图, 不改变窗口状态, 不发送输入;
- 不提交账号、Token、完整个人路径、窗口标题中的个人信息、日志或实机截图;
- 目标身份、截图健康度或坐标映射任一不可信时, 禁止发送输入;
- 本地路径必须继续使用当前 `HTGame.exe`、`UnrealWindow` 和 `NTEInteraction` 行为。

## 2. 当前仓库事实

以下结论来自当前代码, 施工前应再次确认未发生变化。

### 2.1 本地窗口与框架接入

- `src/__init__.py` 中 `GAME_EXE = "HTGame.exe"`;
- `src/config.py` 的 Windows 目标使用 `hwnd_class = "UnrealWindow"`;
- 截图优先级为 WGC, 后备为 `BitBlt_RenderFull`;
- 交互列表当前只有 `NTEInteraction`;
- 分辨率合同为 16:9, 最低 1920x1080, 支持 1080p、1440p、2160p;
- `LauncherTask` 通过 `DeviceManager.ensure_capture()` 在启动器窗口和游戏窗口之间切换。

因此, “把云客户端进程名追加到 `GAME_EXE`”不足以完成适配。它不能表达子窗口选择、
截图区域、输入目标、云会话状态和本地启动器流程的差异。

### 2.2 交互层已有耦合

`NTEInteraction` 继承 `PostMessageInteraction`, 但它还负责:

- QWERTY 物理键位映射;
- 输入锁和 `operate()` 生命周期;
- 点击时的系统鼠标移动与恢复;
- 相对鼠标移动;
- Cursor Sync;
- 必要时激活窗口。

`BaseNTETask.operate()` 和 `move_mouse_relative()` 还通过
`isinstance(interaction, NTEInteraction)` 判断能力。后续若确实需要
`CloudNTEInteraction`, 必须继承 `NTEInteraction` 或先把这些能力改为显式协议;
不能创建一个平行类后假定任务会自动复用它。

### 2.3 Scene 与 Runtime 的现状

`NTEScene` 当前保存登录、截图就绪和战斗等高层状态。`src/runtime/services.py` 负责声音和
OpenVINO 服务生命周期, 并不是目标窗口抽象层。

第一批 PR 不新增 `CloudNTESession` 或 `game_environment.py`。只有真实状态证明现有
`game_capture_ready` 无法表达云会话门禁时, 才引入最小状态模型。

### 2.4 `ok-script 2.0.4` 的接入约束

当前框架根据 Windows 配置中的 `exe`、`title`、`hwnd_class`、`top_hwnd_class` 查找窗口,
再创建 `HwndWindow`、截图后端和交互对象。`ensure_capture()` 是仓库现有的动态切换入口。

施工前必须验证以下问题, 不得从接口名称推断答案:

1. 框架能否仅靠现有配置准确选中云串流子窗口;
2. `top_hwnd_class` 对真实云窗口层级的语义是否合适;
3. WGC 能否直接捕获候选子 HWND;
4. 若必须指定 HWND, `ensure_capture()` 是否保留或覆盖该选择;
5. 窗口重建后, 框架能否安全关闭旧截图资源并重新绑定交互。

若现有扩展点不够, 先提交最小的框架兼容方案或上游 Issue/PR, 不在 `ok-nte` 中复制一套
DeviceManager 和 WGC 生命周期。

## 3. 已知、假设与待决策项

| 类型 | 内容 | 处理方式 |
| --- | --- | --- |
| 已知 | 云客户端不是 `HTGame.exe` | 需要独立目标发现 |
| 已知 | 本地任务依赖统一截图坐标 | 云截图必须标准化为纯 16:9 游戏画面 |
| 已知 | 输入失配可能影响用户当前窗口 | 默认 fail closed |
| 假设 | 云画面位于 Qt 顶层窗口的某个子窗口 | 仅由 Phase 0 验证 |
| 假设 | WGC 可捕获该子窗口 | 仅由 Phase 1 验证 |
| 假设 | PostMessage 可处理主要按键 | 用能力矩阵实测 |
| 待决策 | 截图 HWND 与输入 HWND 是否相同 | 探针和输入试验分别确定 |
| 待决策 | 本地和云端同时存在时选谁 | MVP 明确选择, 不静默猜测 |
| 待决策 | 需要项目内适配还是改 `ok-script` | Phase 1 形成决策记录 |

每个阶段只把已验证事实传给下一阶段。探针结果与假设冲突时, 修改本文, 不修改实机结果。

### 3.1 Probe 初步发现 (2026-09-16, 待完整 Gate 0 确认)

以下为本机只读探针 (`tools/cloud_nte_probe.py`) 的非敏感结论, 仅记录已确认事实:

- 已确认: 串流游戏进程为 `NTECloudGame.exe`, 平台页面为独立进程 `NTECloudBrowser.exe`;
- 已确认: 游戏画面由同进程的多个同级顶层窗口承载, 类名包括 `Qt51517QWindowIcon`、
  `WLCloudGameClient`、`Qt51517QWindowToolSaveBitsOwnDC`; 用户可见的正主是标题为
  `云·异环` 的前台顶层窗口, 其余为叠放在同位置的兄弟渲染面;
- 已确认(推翻第 3 章假设): 串流画面位于顶层窗口本身, **没有承载画面的子窗口**;
- 已确认: 会话状态变化(首页 → 串流)会完全重建窗口, HWND 不跨状态稳定, 重新发现逻辑是必需品;
- 已确认: 串流内切换分辨率/全屏(1600x900 窗口化 → 1920x1080 无边框全屏)**不重建 HWND**,
  仅窗口几何变化, 重建检测不能只依赖 HWND 失效, 还要监控尺寸突变;
- 已确认: PrintWindow 对云客户端 D3D 内容存在 180 度旋转/镜像伪影, 且部分窗口在加载期返回黑帧;
  WGC 能力验证仍是 Phase 1 必做项;
- 已确认: 系统缩放 125%(显示器 120 DPI)下, 云客户端窗口保持物理 1920x1080 且
  PrintWindow 返回完整 1920x1080 帧, 坐标合同不受缩放影响; 窗口自身不跟随缩放改报 DPI
  (仍报 96), 如需应用层适配需重启客户端, 但对截图/坐标无影响;
- 待确认: 输入 HWND(暂定前台窗口为最大候选)、最小化/重连/退出时的窗口树变化;
- 已缓解: 云端画质设置为 1080p 后四个窗口 client 均为 1920x1080, 满足现有合同;
  但默认画质可能低于 1080p, 仍建议启动时检测分辨率并在 UI 提示用户调整云画质设置。

## 4. 目标模型

截图目标和输入目标必须分开描述, 因为二者可能不是同一个 HWND。

建议在 Phase 0 后按真实字段收敛为类似结构:

```python
from dataclasses import dataclass
from enum import Enum


class TargetKind(Enum):
    LOCAL = "local"
    CLOUD = "cloud"


@dataclass(frozen=True)
class GameTarget:
    kind: TargetKind
    process_name: str
    root_hwnd: int
    capture_hwnd: int
    interaction_hwnd: int
```

这只是接口形状, 不是 Phase 0 的强制产物。不要把易变的窗口尺寸、截图帧或平台页面状态
塞进不可变身份对象。

目标解析必须满足:

- 候选评分逻辑是纯函数, 可用合成窗口树测试;
- 实际枚举与 Win32 调用封装在边界层;
- 使用前验证 HWND 仍存在、进程身份未变化、父子关系仍可信;
- 失效后返回“无可信目标”, 而不是继续使用旧 HWND;
- Capture 与 Interaction 共享同一目标快照, 不各自实现一套发现规则。

## 5. 分阶段施工

### Phase 0: 只读 Cloud Probe

新增 `tools/cloud_nte_probe.py`, 只负责收集事实, 不接入应用运行时。

#### 输出字段

对顶层窗口和递归子窗口至少记录:

- PID 和进程名;
- HWND、父 HWND、根 HWND;
- 窗口标题、窗口类;
- visible、enabled、minimized;
- client rect、window rect、DPI;
- 子窗口数量和层级深度;
- 基于标记词的候选原因, 但不直接断言“这就是串流窗口”。

进程路径只允许输出文件 basename。JSON 使用稳定 schema, 例如:

```json
{
  "schema_version": 1,
  "captured_at": "2026-09-15T00:00:00+08:00",
  "windows": [
    {
      "pid": 1234,
      "process_name": "example.exe",
      "hwnd": 100,
      "parent_hwnd": 0,
      "class_name": "ExampleWindow",
      "title": "<redacted>",
      "client_rect": [0, 0, 1920, 1080],
      "candidate_reasons": []
    }
  ]
}
```

#### 隐私与副作用

- 控制台可显示原始标题供本机诊断;
- JSON 默认将标题脱敏, 只有显式 `--include-titles` 才保留;
- 默认不输出完整进程路径和命令行;
- 默认不保存任何截图;
- WGC 单帧诊断必须由显式 `--capture-test` 开启;
- 保存图片必须再显式提供输出路径, 且输出目录保持未跟踪;
- 探针不得激活、移动、缩放、关闭窗口或发送键鼠事件。

#### 单元测试

把以下逻辑写成平台无关纯函数, 用合成数据测试:

- Qt 类名模式只用于标记, 不作为单独命中条件;
- 进程名、类名、父子结构和尺寸的组合评分;
- 多候选排序和歧义返回;
- 标题与路径脱敏;
- JSON schema 和确定性输出。

#### Gate 0

只有得到一份本机留存、人工检查过的探针报告, 并回答以下问题后才能继续:

- 云客户端实际进程名是什么;
- 哪个 HWND 承载纯游戏画面;
- 哪个 HWND 接收键盘与鼠标;
- 客户端首页、串流中、最小化和重连时窗口树如何变化;
- 100%、125%、150% DPI 下窗口几何是否一致。

实机报告、截图和用户环境信息不得提交。仓库测试只使用人工构造的脱敏 fixture。

### Phase 1: 框架接入可行性 Spike

本阶段只验证接入路径, 不修改业务任务。

#### Spike 决策记录 (2026-09-16, 实机)

工具: `tools/cloud_wgc_spike.py`, 直接使用 ok-script 2.0.4 的 rotypes/D3D11 WGC 栈,
未启动完整运行时, 未修改框架。已验证:

- 已确认: `IGraphicsCaptureItemInterop.CreateForWindow` 可直接捕获云异环主窗口
  (前台正主, 标题 `云·异环`, class `Qt51517QWindowIcon`), `item.Size` = 1920x1080,
  与 client rect 精确一致, 帧方向正确无伪影 (对比 PrintWindow 的旋转/镜像);
- 已确认: 另两个同进程幽灵窗口 (`WLCloudGameClient`、`Qt51517QWindowToolSaveBitsOwnDC`)
  对 CreateForWindow 返回 `E_INVALIDARG`, 是不可捕获的辅助渲染面; 失败干净可判别,
  **可捕获性本身是比评分更强的目标判别证据**;
- 已确认: 探针评分最高的窗口 (9 分) 恰是不可捕获的幽灵窗口, 评分模型必须把
  可捕获性或前台状态纳入证据, 否则会选错目标;
- 已确认: `IsBorderRequired=False` 在 build 26200 生效, 无捕获边框;
- 已确认: 帧池刚创建后 `TryGetNextFrame` 可能返回空指针包装对象, 访问属性抛
  NULL COM pointer, 必须容忍 (ok-script 的 FrameArrived 回调已有同等保护);
- 已确认: 重复创建/关闭 WGC 会话可重复执行, 无泄漏或崩溃;
- 结论: **接入路径选择第 1/2 档 (现有配置 + 指定 HWND), 截图栈无需修改 ok-script**。
- 待办 (Phase 1 收尾): 验证 `ensure_capture()`/`HwndWindow` 生命周期对显式 HWND 的
  行为、窗口重建后的重绑路径, 以及本地目标回归。

#### 运行时生命周期决策记录 (2026-09-16, 实机, Gate 1)

工具: `tools/cloud_ok_runtime_spike.py`, 启动真实 headless OK 运行时绑定云窗口。
纯配置 `exe=NTECloudGame.exe + hwnd_class=Qt51517QWindowIcon + title=云·异环`
(嵌套在 `windows` 键下, 与 `src/config.py` 同构) 即可唯一绑定主窗口

- 框架自带 `WindowsGraphicsCaptureMethod` 绑定框架 `HwndWindow` 后直接出帧,
  3 帧 1920x1080, content_ratio 约 0.96;
- `capture.close()` 后重建实例的重绑路径正常, 立即恢复出帧;
- 运行时干净退出, 无泄漏;
- 注意: 绑定后云窗口曾短暂上报 visible=False (失焦场景), 但 WGC 照常出帧,
  后台截图可用性比 PrintWindow 更可靠;
- 注意: ok-script 无任务时不会主动创建 capture_method, 需任务/调用方触发或显式实例化;
- Gate 1 判定: 重复连接/关闭无泄漏 ✅, 不复制框架逻辑 ✅, 无需改上游 ✅;
  本地与云端切换的旧 HWND 清理与本地回归留待 Phase 2/4 实机验证。

按成本从低到高依次尝试:

1. 仅使用现有 `exe`、`hwnd_class`、`top_hwnd_class` 和 WGC;
2. 通过现有目标选择或 `selected_hwnd` 能力指定已验证 HWND;
3. 在 `ok-nte` 增加极薄的 resolver/adapter;
4. 若框架生命周期无法表达, 向 `ok-script` 提交最小扩展。

产出一份短决策记录, 至少说明:

- 选中的接入路径及被否决方案;
- `ensure_capture()` 对目标 HWND 的实际行为;
- 捕获对象关闭和重建路径;
- 是否需要修改 `ok-script`, 以及兼容的最低版本;
- 本地目标回归结果。

#### Gate 1

- 可以重复连接和关闭云截图, 无资源泄漏或崩溃;
- 本地与云端切换不会遗留旧 HWND;
- 不复制框架已有的截图线程和设备管理逻辑;

### Phase 2: 窗口解析与截图标准化

只有 Gate 1 通过后才新增正式窗口解析代码。推荐落点为
`src/interaction/cloud_window.py`; 若最终完全由 `ok-script` 配置表达, 则不新增该文件。

#### 实现记录 (2026-09-16)

- `src/interaction/cloud_window.py` 已落地, 为云窗口识别的唯一事实来源:
  纯评分/选择/脱敏逻辑自探针上移, 探针 (tools/cloud_nte_probe.py) 保留 CLI、
  报告序列化与 PrintWindow 诊断并从此处导入, 两端永不漂移;
- `resolve_cloud_target()`: 按已证实的组合证据 (进程 `NTECloudGame.exe` +
  class `Qt51517QWindowIcon` + 标题 `云·异环`) 唯一解析主窗口; 重建期瞬态重叠
  返回 `ambiguous` 且不给目标 (fail closed); 实机验证 resolved 且
  `wgc_capturable() == True`;
- `assess_frame_health()`: 帧健康纯函数, 判定顺序 HWND 失效 → 无帧 →
  尺寸突变 → 低于 1920x1080 合同 → 比例失配 → 黑帧 (alpha 感知) → OK;
  接入 `game_capture_ready` 属 Phase 4 范围;
- `wgc_capturable()`: 可捕获性判别 (幽灵窗口 E_INVALIDARG), 供目标选择加权;
- 测试: tests/test_cloud_window.py 38 例全绿 (探针兼容重导出 + 新增 resolver/
  health 合成 fixture); 全量回归通过; 实机端到端验证探针与 resolver。

候选选择优先使用经过 Probe 证实的组合证据:

1. 进程身份;
2. 稳定的窗口类或父子关系;
3. 可见性、可用性和合理尺寸;
4. 标题或 Qt 模式仅作辅助;
5. 多个同分候选时返回歧义, 不任选第一个。

截图输出合同:

- 纯游戏内容, 无客户端标题栏、工具栏或黑边;
- 16:9, 且不低于项目当前 1920x1080 最低要求;
- `capture.width`、`capture.height`、`get_abs_cords()` 与实际内容区域一致;
- 1080p、1440p、2160p 复用现有比例坐标与模板缩放;
- 若只能捕获父窗口, 裁剪参数来自窗口几何或校准结果, 不使用固定像素常量。

截图健康检查至少区分:

- 未收到帧;
- 全黑或近黑帧;
- 尺寸突变;
- 内容比例不符;
- HWND 已失效。

健康检查失败时将 `game_capture_ready` 置为 false, 暂停任务并触发有节流的重新发现。

#### Gate 2

- 连续取得 100 帧有效画面;
- 窗口遮挡时行为已记录, 不把偶然成功当后台截图支持;
- 调整 DPI 和客户端尺寸后坐标仍正确;
- 关闭或重建云窗口后不会继续返回旧帧;
- 本地截图和分辨率检查无回归。

### Phase 3: 输入能力与安全门禁

先用现有 `NTEInteraction` 验证。只有目标 HWND、坐标语义或前后台行为确实不同,
才新增 `CloudNTEInteraction`。新增时优先继承 `NTEInteraction`, 以保留当前任务能力判断;
后续若要改为协议应单独提交, 不与云适配混做。

#### 输入能力矩阵 (2026-09-16 实测定稿, 用户实时观察)

背景: 参考先例 Noki-NTE-Auto (v1.6.58 起适配 PC 云异环) 的开源实现, 其关键机制为
"假激活 + 子窗口 PostMessage", 本仓库已独立复现验证。

窗口结构 (动态): 主窗口 `云·异环` → 子窗口 `Qt51517QWindowIcon`/`NTECloudGame` →
子窗口 `WLCloudGameClient`/`WLCloudGame` (真正承载串流画面与输入的表面)。
**层级会动态 reparent** (此前探测时三层均为顶层窗口), 输入前必须用
`FindWindowEx` 链动态定位, 严禁缓存 HWND。

| 输入路径 | OS 投递 | 游戏反应 | 结论 |
| --- | --- | --- | --- |
| 后台 PostMessage → 主窗口 | 成功 | 无 | 客户端忽略 |
| 后台 PostMessage → WLCloudGameClient (未假激活) | 成功 | 无 | 缺激活状态 |
| **WM_ACTIVATE 假激活 + PostMessage → WLCloudGameClient** | 成功 | **有** (角色移动、技能触发, 用户确认) | **最终路径** |
| 前台 SendInput (扫描码) | 注入成功 | 无 | 客户端输入不走消息队列, 该路径废弃 |
| 后台滚轮 | 成功 | 待测 | Noki 先例亦强制前台物理滚轮 |

假激活配方 (来自 Noki 并独立复现):

```python
FindWindowEx(main, 0, "Qt51517QWindowIcon", "NTECloudGame")     # 中间层
FindWindowEx(mid, 0, "WLCloudGameClient", "WLCloudGame")        # 输入表面
SendMessage(child, WM_ACTIVATE, WA_ACTIVE, 0)                   # 假激活
PostMessage(child, WM_KEYDOWN, vk, 0)                           # lparam=0
PostMessage(child, WM_KEYUP, vk, 0xC0000000)                    # 释放
```

- 假激活需要**周期性维持** (Noki 为每 3 秒一次的持续线程), 单次激活会被焦点检测覆盖;
- 已知副作用: 假激活期间客户端在后台持续捕获真实鼠标 (用户在别的窗口移动鼠标,
  游戏内视角会转动); 发送 `WM_ACTIVATE, WA_INACTIVE` 可解除;
- 自动帧差判定不可用: 云串流视频噪声约 2%, 输入反应不可自动判别, 矩阵结论以人眼观察为准;
- 教训: pywin32 `PostMessage` 成功返回 None、失败才抛异常, 必须用 try/except 而非返回值判断,
  否则会漏发 KEYUP 造成粘键 (本次实验实际发生并已即时修复)。

Phase 3 剩余工作: 将上述机制封装为 `CloudNTEInteraction` (继承 `NTEInteraction`),
重写 `send_key`/`click`/`scroll` 的目标定位与假激活维持; 补测后台鼠标点击/滚轮/
相对移动; 能力矩阵的最终策略列随封装补齐。

#### CloudNTEInteraction 封装完成 (2026-09-16)

- 新增 `src/interaction/CloudNTEInteraction.py`, 继承 `NTEInteraction`
  (保留任务侧 isinstance 判断、QWERTY 映射、输入锁、operate 生命周期);
- `hwnd` 属性动态解析到 `WLCloudGameClient` 子窗口 (每次调用重走 FindWindowEx 链,
  子链定位纯函数 `find_cloud_input_child` 落在 `cloud_window.py`, finder 可注入可测试);
- 后台线程每 3 秒假激活; `on_destroy` 停线程并发送 `WA_INACTIVE` 释放用户鼠标;
- 键盘 lparam 覆写为已验证配方 (down=0 / up=0xC0000000);
- 鼠标 `click`/`right_click`/`mouse_down`/`mouse_up`/`move` 直接投递到子窗口,
  不动用户真实光标 (实机验证: 左键攻击、右键闪避均生效);
- `move_mouse_relative` 在云模式为显式 no-op 并告警 (视角旋转不可达,
  需要它的战斗任务暂不支持云模式); 滚轮仍投递但标注不可靠;
- 端到端验证: 真实 OK 运行时 (config interaction=[CloudNTEInteraction]) 绑定云窗口,
  经 `CloudNTEInteraction` 发送 E/W/点击全链路成功, 干净退出。

不得预先承诺优先级。云客户端可能完全忽略后台消息, 也可能要求键鼠发送到不同子窗口。

#### 输入门禁

每次派发输入前必须在同一目标快照上验证:

- HWND 有效且仍属于预期进程;
- 捕获健康且最近获得有效帧;
- 坐标位于内容区域;
- 没有未解决的多目标歧义;
- 需要前台输入时, 前台窗口确认成功。

若使用物理鼠标或 `SendInput`:

- 只在明确能力降级时启用;
- 沿用现有输入锁和鼠标恢复路径;
- 前台窗口校验失败则不发送;
- 任务停止、异常和窗口消失时释放所有按键;
- UI 和日志明确说明该操作会影响用户当前鼠标或前台窗口。

#### Gate 3

- 按键 down/up 配对, 停止任务后没有粘键;
- 点击、拖拽、滚轮和相对移动均使用正确坐标系;
- HWND 失效或截图异常后的下一次输入被拒绝;
- 前台 fallback 不会向其他窗口发送输入;
- 能力矩阵记录真实结果和测试环境。

#### Phase 4 运行时接入实现 (2026-09-16)

- `src/__init__.py` 新增 `CLOUD_EXE = "NTECloudGame.exe"`;
- `LauncherTask`:
  - `DynamicConfig.CLOUD_CAPTURE_CONFIG`: exe=`NTECloudGame.exe` + class
    `Qt51517QWindowIcon` + 标题 `云·异环` + interaction=`CloudNTEInteraction` +
    仅 WGC;
  - `run()` 自动检测: 先探云客户端进程 (存在 → 云分支), 再走本地启动器流程
    (本地用户零改动); 云分支等待窗口可见 → `ensure_capture(云配置)` →
    连接确认 → 分辨率校验 → `set_game_capture_ready(True)`;
  - `_find_process_window` 对云进程按精确标题 `云·异环` 过滤, 避免选中幽灵窗口;
  - 抽出 `_wait_for_capture_connection` 复用于本地/云两条路径;
- `BaseNTETask.update_capture_health()`: 有节流 (默认 5 秒) 的截图健康检查,
  失败时置 `game_capture_ready=False` 并告警; `NTEOneTimeTask.run` 在就绪门禁前调用;
- 已知限制 (写死在实现里, 非遗留): 云模式下相对鼠标移动 (视角旋转) 不可用,
  需要它的战斗任务不支持云模式; 滚轮后台投递不可靠;
- 测试: tests/test_cloud_integration.py 12 例 (配置内容/自动检测分支/精确标题过滤/
  健康检查状态迁移与节流/一次性任务门禁), 云相关测试 50 例全绿。

### Phase 4: 运行目标与简单任务

在 Gate 2 和 Gate 3 通过后, 再把云目标接入应用启动流程。重点检查
`src/config.py`、`LauncherTask`、`NTEScene.game_capture_ready` 和设备选择 UI。

MVP 选择规则:

- 只存在本地目标时选择 Local;
- 只存在一个可信云目标时选择 Cloud;
- 两者同时存在或出现多个云目标时, 要求用户明确选择;
- 不用“优先 Local”的静默规则掩盖歧义;
- 云模式不复用本地启动器的启动、路径回写和最小化流程。

任务兼容顺序按风险递增:

1. 一个只包含稳定 UI 点击和识别的现有任务;
2. Daily 中一个边界清晰的任务;
3. Fishing;
4. DailyRoutine;
5. AutoCombat;
6. AutoHeist。

失败统一归类为 Target、Capture、Interaction、Scene 或 Task。只有确认云端游戏 UI 本身存在
差异后才修改 Task, 且修改必须有独立证据和回归测试。

仅当平台首页、排队、加载或重连状态确实需要阻止 `NTEScene` 运行时, 才增加轻量的云会话
状态。它只负责回答“当前是否已进入可供 `NTEScene` 判断的游戏画面”, 不负责登录、购买
或网络管理。

#### Gate 4

- 至少一个既有简单任务无需云端条件分支即可完成;
- 本地启动、手动连接和已有任务无回归;
- 多目标场景不会自动选错;
- 云平台页面不会被误判成游戏就绪。

### Phase 5: 声音, 独立立项

当前声音触发和后台音频路由都直接依赖 `GAME_EXE`。云端音频可能由不同进程、子进程或
音频会话输出, 必须独立调查。

继续保持 WASAPI/系统音频层读取。不得改为进程注入、音频 API Hook 或内存读取。

## 10. 结论

正确的第一步不是修改 `GAME_EXE`, 也不是开发自动战斗, 而是取得真实窗口、截图和输入
证据。只有依次通过 Probe、框架接入、截图、输入和简单任务五个关卡, 才能确认云异环
确实可以作为 `ok-nte` 的第二种 Windows 运行目标。

该顺序既保护本地用户, 也让后续 agent 的每个任务都有明确输入、产物、禁止项和停止条件。
